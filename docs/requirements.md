# 要件

LT・勉強会の発表にリアルタイムでコメントといいねを送れるサービス「LeacTion!」を、Cloudflare 上に作り直す。参加者はログインなしで使え、主催者はアカウントなしの秘密 URL で管理する。

## 位置づけと方針

- 旧リポジトリ（tegehoge/leaction）はコミュニティ開発を想定していたが、実質 1 人で開発・運営しているため、mather の個人リポジトリとして新規に作る。旧データは移行しない
- 基盤は Cloudflare Workers・Durable Objects・D1。まずは無料プランで運用する
- フロントエンドは SolidJS を継続する（学習も兼ねる）。SUID は外し、デザインはゼロから作る
- 設計の軸は 2 つ。スマホで「見る・書く・発表を切り替える」が楽なこと。主催者がアカウント登録なしで、作成から当日の管理まで完結できること

## 現行版の振り返り

現行版は 2 世代ある。

- v1（2020〜）: Vue 3 + Cloud Functions（Express）+ Firestore。パスワード方式の編集と、終了イベントの JSON アーカイブを持っていた
- v2（2023〜、最終コミット 2024/4）: SolidJS + SUID。Firestore をブラウザから直接使う

### 良かった点（引き継ぐ）

- 参加者はログイン不要で、開いてすぐコメントできる
- コメントを発表ごとに分け、`?tid=` で特定の発表を URL 共有できる
- 最下部を見ているときだけ自動スクロールし、それ以外は「最新のコメントを見る」を出す
- いいね（自分のコメントには不可）と、自分のコメントの削除
- コメント内の URL は、開く前に確認ダイアログを出す
- QR コード・URL コピー・X での共有
- 発表枠のドラッグ並べ替え
- ローカルエミュレータでの開発と、PR ごとのプレビューデプロイ
- v1 の「終わったイベントを静的 JSON にして長くキャッシュする」発想

### 課題と新版での対応

| 課題 | 新版での対応 |
| --- | --- |
| 共同管理者リクエストの一覧を、匿名を含む誰でも丸ごと書き換えられる | リクエストの仕組み自体を廃止。作成者が共同管理者 URL を発行する |
| いいねした人の一覧を丸ごと書き換えられ、水増し・削除ができる | いいねは 1 件ずつの行で持ち、サーバーが投票者を決める |
| コメントの投稿者・文字数・発表 ID・時刻を検証していない | 全てサーバー側で決定・検証する |
| Storage が認証済みなら全パス読み書き可能 | ファイルアップロード機能を持たない |
| アカウント（表示名）を全件一覧できる | アカウントを持たない |
| 管理者が他人のコメントを消せず、荒らしに対処できない | 非表示・投稿者単位の一括非表示・受付停止を用意 |
| イベント保存が丸ごと上書きで、同時編集や途中の変更が消える | 操作ごとの差分更新を即時反映。書き込みは 1 イベントを 1 か所で直列処理 |
| イベントや発表枠を消してもコメントが残る | イベントのデータを 1 か所にまとめ、削除時にまとめて消す |
| 匿名利用後に Google ログインすると別ユーザーになり、過去のコメントを消せない | 参加者 ID はログインと無関係の Cookie で持つ |
| 全発表のコメントを全員が購読し、読み取り課金が「参加者数×コメント数」で増える | WebSocket で差分だけ配信し、待機中は休止させる |
| イベント URL をシェアしても OGP が常に「LeacTion!」 | イベントページの HTML にイベントごとの OGP を差し込む |
| QR コードを外部サービスで生成し、URL が第三者に渡る | ブラウザ内で生成する |
| 共同管理者リクエストが通知されない | リクエストの仕組みごと廃止 |

1. URL の `?tid=` で指定された発表
2. （「発表中」を導入した場合）発表中の発表
3. そのブラウザで前回見ていた発表
4. 1 番目の発表

## 非機能要件

- **規模**: 1 イベントあたり参加者数十〜100 人、コメント数百件を想定。無料プランの上限（DO: 1 日あたりリクエスト 10 万、書き込み 10 万行）に収める
- **即時性**: 投稿から他の参加者の画面に出るまで、体感で待たされないこと
- **サクサク感**: 普通の操作で連投制限や確認画面に当たらないこと
- **スマホ優先**: 390px 幅を基準に設計し、タップ領域は 44px 以上
- **再接続**: 電波が切れても自動で再接続し、取りこぼしを埋める
- **言語**: 日本語のみ
- **不意の離脱を防ぐ**: イベント中に誤タップでイベントページを離れないこと。イベントページから外へ出る導線は 1 タップで発火させない

## 権限モデル

権限は「人」ではなく「どの URL を持っているか」で決める。イベントごとに管理者が変わり、そのときしか管理しないことが多いため、アカウントは持たない。

| 操作 | 作成者 URL | 共同管理者 URL | 参加者 |
| --- | --- | --- | --- |
| コメント、いいね、自分のコメントの削除 | ○ | ○ | ○ |
| イベント情報・発表枠の編集 | ○ | ○ | × |
| コメントの非表示・一括非表示・受付停止 | ○ | ○ | × |
| 共同管理者 URL の発行・無効化 | ○ | × | × |
| イベントの削除・復元 | ○ | × | × |

作成者と共同管理者を分ける理由は 3 つ。

- 秘密 URL は Slack や画面共有で漏れる前提で考える。共同管理者 URL が漏れても、作成者が無効化して出し直せる
- 削除は取り返しがつかないので、最も漏れにくい URL だけに持たせる
- 共同管理者リクエストの仕組みが不要になる（作成者が URL を渡すだけ）

### トークンの扱い

- 形式: `/e/{eventId}/manage#k={token}`。`#` 以降はサーバーのログにも Referer にも載らない
- トークンは十分な長さの乱数（例: 32 バイト）で作り、DB には SHA-256 のハッシュだけを保存する
- 管理画面を開いたら、トークンをサーバーに送って署名付き HttpOnly Cookie（イベント単位の管理セッション）に入れ替え、アドレスバーから `#k=` を消す
- ハッシュしか持たないため、作成者用 URL は作成完了画面を閉じると再表示できない。そのため完了画面で、コピー・自分宛てメール（`mailto:`）・保存確認チェックを用意する
- 共同管理者 URL も発行時に一度だけ表示する。無効化すると、その URL から作られた管理セッションも失効させる

### 参加者の識別

- 初回アクセス時に Worker が匿名 ID を発行し、署名付き HttpOnly Cookie で持たせる
- コメントの投稿者やいいねの投票者は、常にサーバーが Cookie から決める（クライアントからは渡さない）
- 管理画面には匿名 ID の先頭数文字だけを出し、同じ人の投稿だと分かるようにする
